## 이미 잘하고 있는 것 (강조할 점)

1. **검증을 다른 컨텍스트로 분리** — FINISH에서 `baton-verifier` 서브에이전트에 "작업 ID만 넘기고 구현 설명은 덧붙이지 않는다"(AGENTS.md:138), verifier는 "구현한 쪽 설명은 판단 뒤에 참고만"(baton-verifier.md:19).
   MP는 "뒤 단계를 숨기는 건 **진짜 컨텍스트 경계**(서브에이전트, 핸드오프)를 넘을 때만 효과가 있다"고 하는데, baton은 그걸 정확히 씁니다.
2. **기계로 확인되는 완료 조건** — HANDOFF 3단계의 `check-active.mjs`, `preflight`의 [멈춤]/exit 1. "다 채웠다"를 에이전트 판단이 아니라 스크립트가 판정합니다. MP 기준으로 가장 강한 형태(확인 가능 + 빠짐없음)입니다.
3. **`Git Wins`라는 핵심 단어** — "문서와 실제가 다르면 Git과 테스트를 믿고 문서를 고친다"를 두 단어로 압축했고, status.mjs 출력(`! Git Wins`)·CLAUDE.md·AGENTS.md에서 같은 토큰으로 반복됩니다. MP가 말하는 leading word의 교과서적 예입니다.
4. **위험 규칙은 긍정형과 짝지음** — "절대 하지 않는 것" 목록 앞에 "실행 전에 멈추고, 무엇을 왜 하는지 설명한 뒤 승인을 받는다"(AGENTS.md:46)가 있어서, 금지만 던지지 않고 "대신 할 행동"을 줍니다.
5. **Git에 있는 건 다시 적지 않기** — STATUS.md "Git에서 알 수 있는 세부 변경 내역은 쓰지 않는다", ACTIVE "긴 에러 로그 대신 요약 + 재현 명령". MP의 `handoff` 스킬 핵심 규칙("다른 산출물에 있는 건 복사 말고 경로로 참조")과 같습니다.
6. **이미 스스로 발견한 같은 원리** — 작성자 기록: "서브에이전트 형식은 받는 쪽 정의만으로 안 지켜진다. 부르는 쪽이 보는 description과 호출 문구까지 맞춰야 한다." 이게 MP가 말하는 **context pointer**(설명 한 줄이 언제·얼마나 확실히 불리는지를 결정) 이론과 같은 결론입니다. 측정으로 먼저 도달했다는 점이 눈여겨볼 만합니다.

## 고칠 점 (효과 큰 순서)

### 1. 항상 실리는 분량이 큼 → 절차를 별도 파일로 빼기 ⭐

**현재**
- baton이 깔린 프로젝트의 모든 세션, 모든 턴에 실리는 것: `GLOBAL_RULES.md` 7,046자 + `AGENTS.md` 16,899자 + `CLAUDE.md` 1,179자 = **약 2만 5천 자**.
- 그중 "그 상황에서만" 필요한 것:
  - AGENTS.md 4~8절(START·RESUME·HANDOFF·FINISH·HELP 절차): **7,443자 (AGENTS.md의 44%)**. 질문·조회만 하는 턴에도 실려 있음(그런 요청엔 절차를 안 쓴다고 20행에 직접 적혀 있음).
  - GLOBAL_RULES.md의 "baton 업데이트"·"audit 업데이트" 절차(51~69행): **3,623자 (GLOBAL_RULES의 51%)**. 1년에 몇 번 쓸 절차가 **모든 프로젝트의 모든 세션**에 실림.
- 비교: MP 저장소에서 가장 긴 SKILL.md가 170줄이고, 그것도 필요할 때만 불립니다. AGENTS.md는 176줄이 항상 실립니다.

**MP 기준** — "모든 경우에 필요한 건 본문에, 일부 경우만 필요한 건 포인터 뒤로." 길이 자체(sprawl)가 주의력을 흩뜨린다는 주장.

**이상한 점(일관성)** — 설치 절차는 이미 `INSTALL_FOR_AGENT.md`로 빠져 있고, audit 설치도 `SETUP_FOR_AGENT.md`로 빠져 있는데, **업데이트 절차만 GLOBAL_RULES 본문에 있습니다.** 같은 패턴을 쓰면 됩니다.

**제안**

**위험** — 포인터 문구가 약하면 에이전트가 파일을 안 읽고 기억으로 절차를 흉내 냅니다. MP도 "포인터 문구를 먼저 날카롭게, 그래도 안 되면 다시 인라인"이라고 합니다.

### 2. 모호한 완료 기준 2곳

**(a) Micro Update의 발동 조건** — AGENTS.md:76 "의미 있는 단계가 끝날 때마다". "의미 있는"은 에이전트가 판정할 수 없는 기준이라, 바쁜 작업 중엔 건너뛰기 쉽습니다(MP의 premature completion).
- 제안: 관찰 가능한 사건에 묶기 → **"커밋할 때마다"** ACTIVE.md의 Current State·Next Exact Step을 그 커밋 내용에 맞춘다. 이미 78행에 "같은 커밋에 넣는다"가 있으니, 두 줄을 하나로 합치면 기준이 명확해집니다.
- 확인: HANDOFF 시점에 `git log -p tasks/ACTIVE.md`로 wip 커밋 중 ACTIVE.md가 안 바뀐 비율.

**(b) baton-verifier "확인할 것" 3번** — "변경이 다른 기능에 영향을 줄 만한지"(baton-verifier.md:31). 다른 항목은 근거가 분명한데 여기만 "~할 만한지"라 검사량(demand)이 약합니다.
- 제안: "변경된 함수·export를 쓰는 곳을 Grep으로 찾아, 각 사용처가 여전히 맞는지 근거 한 줄"처럼 **빠짐없음이 보이는** 기준으로.
- 결과 형식에도 "영향 범위: <찾은 사용처 수>곳 확인" 한 줄 추가하면 형식이 기준을 강제합니다.

## 바꾸지 않는 게 나은 곳 (MP 규칙과 일부러 다르게 가는 곳)

- **0절의 트리거 동의어** ("넘길게", "여기까지", "멈추자") — MP는 "동의어 나열은 같은 갈래를 두 번 쓰는 것"이라 줄이라고 하지만, baton은 **비전공자가 자연어로 부르는 것**이 설계 목표라 실제 사용자가 쓰는 말을 늘어놓는 게 맞습니다. 표 몇 줄이라 비용도 작음.
- **"사용자는 비전공자다", "한국어로"가 여러 파일에 반복** — 중복처럼 보이지만 각 파일이 다른 에이전트·다른 앱(Codex, 채팅 앱)에서 단독으로 읽히므로 필요합니다.
- **ACTIVE.md를 커밋해 남기는 방식** — MP의 `handoff`는 임시 폴더에 저장하고 버리지만, baton은 다른 에이전트·다른 컴퓨터로 넘기는 게 목적이라 Git에 남겨야 합니다. 이건 차이점으로 설명하면 좋은 포인트입니다.

## 비교: "같은 문제, 다른 무게"

| | MP `handoff` | baton |
| --- | --- | --- |
| 크기 | 15줄 스킬 1개 | 절차 + 스크립트 7개 + 서브에이전트 + 훅 |
| 저장 위치 | 임시 폴더 (1회용) | Git의 task 브랜치 (에이전트·컴퓨터 간 공유) |
| 완료 판정 | 없음 (에이전트 판단) | `check-active.mjs`, verifier PASS/FAIL |
| 어긋남 처리 | 없음 | `Git Wins` (문서 vs 실제 불일치 감지) |
| 실패 기록 | 없음 | Failed Attempts (반복 방지) |
| 대상 사용자 | 개발자 본인 | 비전공자 + 여러 에이전트 |

이 표에 "무게를 더한 대가로 무엇을 얻었는지"를 숫자로 붙이면(stats의 이어받기 후 첫 수정까지 요청 수 등) "실패를 다루는 설계"와 "평가 체계"를 함께 보여 줄 수 있습니다.

## 추가 제안: 금지 규칙을 훅으로 (평가, 2026-11-05)

> 리뷰 추가 제안: AGENTS.md에 "금지"로만 적힌 것 중 main 직접 커밋, `--no-verify`, 비밀값 검사 없는 커밋은 훅으로 옮길 후보다. 셋 다 코드로 판정되고 어기면 비싸다. 참고 예제는 mattpocock의 git-guardrails-claude-code 스킬(위험한 git 명령을 막는 훅 설치).

**방향:** 동의한다. 훅은 프로그램이 판정하므로 토큰이 들지 않는다. 다만 세 가지는 성격이 달라서 그대로 옮기면 둘은 문제가 생긴다.

### 훅 두 종류
- **git 훅(pre-commit):** 어느 에이전트·사람이 커밋해도 걸린다. 하지만 `--no-verify`로 건너뛸 수 있다.
- **에이전트 도구 훅(Claude Code PreToolUse):** 명령 실행 직전에 검사한다. `--no-verify`를 잡을 수 있는 건 이쪽뿐이다. Codex 지원은 확인하지 않았다.

### 항목별
| 항목 | 평가 | 설계 |
| --- | --- | --- |
| 비밀값 검사 없는 커밋 | 가장 가치 큼(새면 키 재발급) | pre-commit에서 `scan-secrets.mjs`. 기존 훅 관리 도구(husky, lefthook, pre-commit 등)가 있으면 [멈춤]으로 묻는다 |
| `--no-verify` | 맞음 | PreToolUse에서 거부. 짧은 옵션 `-n`과 `-c core.hooksPath=…` 덮어쓰기도 포함 |
| main 직접 커밋 | 그대로 막으면 안 됨 | "거부" 대신 "확인 요청(ask)". 승인된 병합·squash(`MERGE_HEAD`, `SQUASH_MSG`가 있는 상태)와 설치 첫 커밋(`chore: initial commit before baton`)은 막으면 안 된다. 진짜 비싼 건 커밋이 아니라 main push·force push이므로 그것부터 ask |

### 우선순위
1. 비밀값 검사 pre-commit 훅
2. `--no-verify` 거부 + main push·force push 확인 요청
3. main 커밋 확인 요청

### 비용과 한계
- **설치 도구:** place.mjs·sync.mjs는 지금 SessionStart 그룹만 합친다(`place.mjs`의 HOOK_FILES). PreToolUse 합치기를 새로 만들어야 한다. doctor 검사와 시험도 필요하다.
- **PC마다 설치:** git 훅 위치(`core.hooksPath`)는 저장소의 로컬 설정이라 Git으로 따라오지 않는다. PC마다 설치해야 한다.
- **우회:** 문자열 검사라 작정하면 돌아갈 수 있다. 실수를 막는 장치이지 보안 경계가 아니다.

### 확인 안 함
- git-guardrails-claude-code 원문(정확히 무엇을 막는지). 만들 때 읽는다.
- Codex의 PreToolUse(명령 실행 전 훅) 지원 여부.
